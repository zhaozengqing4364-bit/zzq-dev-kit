## Context
See proposal.md. Existing user skills are portable but installed manually. The target may be empty, dirty, or have a custom OpenSpec/store setup. Installation must not infer permissions to rewrite those assets.

## Goals / Non-Goals
Deliver a Node 22+ ESM CLI with deterministic installation and recoverable local file mutations. The first release supports Codex and Claude on user/project scopes. It does not execute target application tests, migrate business specifications, force-replace installations, install hooks, or change credential/model configuration.

## Decisions
- Package the official OpenSpec 1.14.2 engine as an exact dependency and expose `zzq-dev-kit openspec`. New configuration is generated by that engine in a temporary staging directory with tools disabled; existing config stays byte-identical. A project launcher uses the same release through npx when a global OpenSpec is absent.
- Default `init` installs skills to user scope for Codex, with explicit project scope or Claude selection. The eleven skill folders are a versioned snapshot. An identical unowned file can be reused; a differing unowned file is a conflict. Existing symlinks are never traversed for writes or silently replaced.
- Preserve global AGENTS. Add a bounded managed pointer block to project AGENTS (or the effective AGENTS.override.md) and write a generic guide/launcher under `.zzq-dev-kit`. Rules outside the block and existing config are preserved. Project facts are inspected by the setup skill; no fabricated package commands.
- Build a complete change plan first, check content hashes and ancestor symlinks, then serialize writes through a tool-owned lock. Store before/after data and status in the user's tool-state directory. Atomic per-file rename plus durable journal enables explicit rollback/recovery; it is not a cross-filesystem atomic transaction. A failed run attempts rollback only when current files match known versions.
- Separate user installation ownership from project manifest. Only relative project paths are committed; recovery data remains local to the user. No automatic removal or adoption of divergent older installations.
- `doctor` checks actual owned files, skill links and OpenSpec resolution without running application scripts. `upgrade` changes only known managed content that has not drifted. Existing schema changes are never part of upgrade.

## Risks / Trade-offs
- Filesystem races cannot be eliminated by hashes alone: serialize this tool, reject symlinks, recheck before each write and refuse recovery on external drift.
- A killed process may leave a lock/journal: explicitly recover a recorded transaction; never expire another active writer's lock by time.
- Runtime resolution after npx cache cleanup can need network: the generated launcher pins the published kit version and never adds application dependencies.
- Per-agent copies are portable on Windows; versions and checksums keep their installed snapshot coherent. Existing user-managed links require a user migration decision rather than implicit rewriting.

## Migration Plan
Build and test only in this standalone repository and temporary homes. Preserve the user's currently installed skills. Publish a minimal allowlisted tarball, test it through npx, run multi-OS CI, then publish an npm version. Any migration of the user's existing divergent skills is a separate concrete decision.
