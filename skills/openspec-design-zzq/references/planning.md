# 规划协议

已读common.md后使用。此协议服务design的新建、继续、补全、修订及已授权实施的规划缺口修复，不扩大各入口的任务终点。

## 从实际图推进

1. 运行`openspec status --change <name> --json`（必要时附已选store）。读取schemaName、applyRequires、artifacts及requires边，不硬编码六阶段。
2. 完整规划的目标集合是applyRequires及其传递依赖；用户明确限定的产物按其范围推进。done节点的上游也要核对存在，不能因提前写了tasks就认为依赖齐备。
3. 先检查所需glob产物的具体文件完整性。根据对应instructions和有效上游决定需要哪些文件；若Schema采用能力增量规格，则按已确认范围核对完整能力路径。保留有意省略或skipped，不推断任何glob只有一个文件。
4. 对待创建的ready产物调用`openspec instructions <artifact-id> --change <name> --json`。读取实际context/rules/instruction/template/dependencies；已读依赖无变化可复用。skipped依赖不寻找文件。
5. 在实际范围内调查后写产物。用模板组织本次独有内容，引用上游事实；不用通用“以后研究”任务代替当前必要调查，不复制敏感资料和长日志。
6. 校验路径及内容，写后刷新status。需要补多个glob文件时只补缺口，不覆盖并发改动。已有产物的实质修订按下文修订规则检查影响。
7. 条件产物省略必须由当前Schema/instruction明确支持，并按CLI实际机制处理；不能凭主观判定写入blocked产物或跳过必要契约。依赖规则不清时只暂停相关部分并核对。
8. 直到本次目标集合内容充分且CLI状态一致；只要求下一份就不扩大成全套。已授权完整实施交给apply继续，规划请求到此结束。

## 内容判据

先按当前Schema的实际产物映射下面的职责，它们不是固定文件清单或额外阶段。没有独立调研或验收产物时，将调查依据、成功标准和验证安排放在现有提案、规格、设计或任务的合适位置；不额外创建discovery.md/acceptance.md来满足技能示例。

重要决定未清楚时使用[澄清与探索方法](shaping-methods.md)：先查事实，再按依赖提问或研究；仅在明确原型授权时使用prototype，决定落回对应产物。大任务的决策地图只保留问题与指针，不另建issue状态机，也不提前把模糊范围拆成实施任务。

- Discovery：真实入口、现状、目标、差距及关键未知可区分；新项目先确定关键路径和技术可行性风险。
- Proposal：用户收益、范围/非目标及更小方案是否够用；能力路径准确。
- Specs：可观察规则、不变量和具体例子，适用的明确拒绝/未知/部分成功与恢复；不掺实现步骤。
- Design：实际模块与状态归属、直接消费者、必要事务/外呼边界、资源成本和风险验证；新机制有收益依据。
- Acceptance：依据业务预期定义正常例与关键反例、最低有效证据、通过条件及未验限制。与方案对齐，依当前产物图安排。
- Tasks：每片对应完整用户结果、位置/依赖、规则和验证；无需另建状态机，也不固定最终全仓再测。

这些是通用设计职责，名称仅帮助理解。完成目标由当前Schema、CLI依赖和用户本次范围决定，不强制六阶段或某个Schema名称。

## 可交接条件

实施者不用猜重要业务语义，核心操作的权限/状态/结果与恢复明确，验收者能判断对错；高影响未知已经验证或仅阻塞依赖切片。普通可逆实现细节可以在实施时完善。

产物文件齐备、严格校验通过分别只证明其对应层级。定向运行`openspec validate <change> --strict --no-interactive`，不为一个change检查所有历史。未实际运行业务不声称业务通过。

## 修订已有决定

把新事实或已确认决定放回其拥有位置，核对前后依赖：后续设计也可能要求修订早期范围或规格；实现偏离不代表应改规格迁就代码。在已有授权内同步当前Schema中直接受影响的设计、验证安排和实施任务，标明哪些实现与旧证据失效。新重大选择保持待决，未受影响的事实和完成项保留。

只补当前Schema实际缺失的产物；不会因用户说“继续”新建重复change，或把已存在文件全量重生成。修订完成后定向严格校验；已授权实施继续apply，仅改方案则交付到此。
